# シーンIMG抽出ツール

[日本語ドキュメント](../../README.md) | [English](../../../en/technical/reference/scene-extractor.md) | [シーンツール（英語）](../../../../tools/scenes/README.md) | [シーンのレイアウトと出現条件](../architecture/scene-layouts.md)

ゲームの `ANA/INFO_*/*.IMG` を読み込む抽出ツールです。
セクションのオフセットを確認し、識別できるデータを取り出して、残りのバイト列を未分類のデータとして保存します。
入力ファイルは変更しません。

```sh
make extract-scene SCENE=/path/to/ANA/INFO_PRT/WAL_B020.IMG
```

出力先は `assets/exports/us/scenes/WAL_B020/` です。
`VERSION=jp` で日本版用の出力先を選び、`SCENE_OUTPUT` で親ディレクトリを変更できます。
抽出先には、まだ存在しないディレクトリを指定します。生成されたファイルはGitの管理対象外です。

抽出済みのANAディレクトリにある、対応するすべてのシーンを処理するには、次のようにします。

```sh
make extract-scenes ANA=/path/to/ANA
```

一括抽出では `INFO_*/*.IMG` を読み込み、グループ名とシーン名を出力先に残します。
たとえば `assets/exports/us/scenes/INFO_PRT/WAL_B020/` です。
日本版のANAディレクトリを使うときは `VERSION=jp` を指定してください。
一括抽出でも `SCENE_OUTPUT` を使えます。

各シーンの出力先は、すべて新しいディレクトリである必要があります。
処理を始める前に、既存の出力先がないか確認します。
不正なシーンがあると、そのファイル名を表示して停止します。それまでに抽出したファイルは残ります。
ほかの種類のIMGファイルは対象に含めません。

## 出力

| ファイル | 内容 |
| --- | --- |
| `byte-map.yaml` | 元のIMG内のオフセット、サイズ、抽出先ファイル名 |
| `header.bin` | セクションのオフセットを格納した40バイトのヘッダー |
| `textures/000.tim` など | 元のファイル順に並ぶ、完全なTIMデータ |
| `portraits/000.bin` など | パレットとピクセルを含む、顔画像のレコード全体 |
| `chests/<layout-index>.yaml` | 宝箱の情報と元のレコードのバイト列 |
| `unknown/<offset>.bin` | 識別済みのデータとしては抽出していない部分 |

バイトマップの各YAMLエントリーは、元のファイルの連続したバイト範囲に対応します。
`offset` は元のIMG内の位置を16進数で示し、`size` はバイト数です。
範囲は `offset + size` の直前までです。`file` は出力ディレクトリからの相対パスです。
宝箱の場合、`size` は元のレコードの48バイトで、YAMLファイルの長さではありません。

TIM、顔画像、識別できた宝箱のレコードには、それぞれ1件のエントリーを作ります。
同じTIMへの参照が複数あっても、抽出するTIMファイルは1つです。
残りの範囲は `unknown_data` として扱います。スクリプト、テキスト、形状データ、コンテナーのテーブルなどもここに含まれます。
一部のフィールドは意味がわかっていますが、このツールでは生のバイト列のまま残しています。

宝箱の詳細は専用のYAMLファイルに置くので、バイトマップには各データの位置だけを記録します。
ほかのデータと未分類の部分はバイナリのままです。
元のIMGを復元するには、各宝箱の `record_bytes` を16進数の文字列からバイト列に戻し、
バイトマップの順序に従ってほかのファイルと連結します。

## 宝箱のレコード

レイアウトセクションは、u32の件数と、それに続く48バイトの
[`FieldLayoutRecord`](../../../../include/overlays/field/field_interaction_start.h)で構成されます。
宝箱も、ほかのアクターと同じレコード構造を使います。
抽出ツールは、共通の宝箱リソースの選択値と初期化スクリプトを確認してから、そのレコードを `chest` として扱います。

YAMLには、レイアウトのすべてのフィールドを出力します。
`condition.variable_ref` と最小値・最大値、制御情報と位置の各フィールド、リソースの選択値、
有効なイベント、16個すべてのスクリプト・パラメータースロットを確認できます。
宝箱の設定として、`x`、`z`、`item_id`、`collection_variable_ref`、`alternate_facing` も表示します。
アイテムは `scripts[4]`、収集状態の変数への参照は `scripts[5]` のビット0から14に入っています。
ビット15は、向きを切り替えるフラグです。`record_bytes` には、元のレコード全体を16進数で保持します。
読みやすく展開したフィールドは、保存されているレコードの内容を示すものです。それらを編集しても `record_bytes` は変わりません。

たとえば `WAL_B020.IMG` には、位置 `(395, 180)`、アイテム `0x96`、収集状態の変数への参照 `0x0BC0` の宝箱があります。
レイアウトレコード2なので、`chests/002.yaml` として出力されます。
イベントスクリプトは未分類のデータに残ります。このツールはスクリプトを実行せず、アイテム名の解決も行いません。
別の初期化スクリプトを使うレコードは、内容を確認できるまで生のデータとして扱います。

## 対応する形式

ヘッダーには、リトルエンディアンのu32オフセットが10個あります。
順に、レイアウト、イベントスクリプト、文字列、アクターのスクリプト、レコード、アクター、形状データ、画像、顔画像、グループ境界です。
最初のセクションはバイト40から始まります。
オフセットは所定の境界に揃い、順番どおりに並び、ファイル内に収まっている必要があります。

画像セクションには、オフセットテーブルと、それに続くTIMデータがあります。
TIMの検証には既存のパーサーを使います。
顔画像セクションは、件数と1件1,184バイトのレコードで構成されます。
各レコードは32バイトのパレットと、1ピクセル4ビットの48×48ピクセルの画像を持ちます。顔画像はTIM形式ではありません。

対応しているのは、ここで説明したシーンIMGの構成です。すべてのIMG形式や圧縮ファイルを扱えるわけではありません。
ゲーム側でこれらを読む処理は、[シーンローダー](../../../../src/overlays/field/scene/field_scene_transition.c)と
[顔画像の定義](../../../../src/overlays/field/ui/field_text.c)を参照してください。

Python側も、この構造に沿っています。
`SceneHeader` がヘッダー、`FieldLayoutRecord` がレイアウトレコードを表します。
`read_chests()`、`read_textures()`、`read_portraits()` が、それぞれのセクションを処理します。
`AssetRange` は抽出するバイト範囲を表す型で、ディスク上の構造そのものではありません。
