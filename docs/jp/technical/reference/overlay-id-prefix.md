# オーバーレイのIDプレフィックス

[日本語ドキュメント](../../README.md) | [English](../../../en/technical/reference/overlay-id-prefix.md)

実装済みです。Cソースをビルドするすべてのオーバーレイでは、専用の `overlay_header.c` にヘッダーワードを置き、最初にリンクしています。
この構成で、北米版の全17オーバーレイがディスク上のSHA-1と一致します。

## 概要

Legend of Manaには、ディスクから読み込む複数のオーバーレイがあります。
それぞれの先頭には、そのオーバーレイのモジュールIDを表す4バイトのワードがあります。
コードやデータは、その直後のオフセット `0x4` から始まります。

現在の調査では、実行中にこの値を読む処理は見つかっていません。
メイン実行ファイルはオーバーレイを決まったロードアドレスへ読み込み、その中の固定アドレスを呼び出します。
そのため、このIDプレフィックスはゲームの処理に必要な値というより、開発ツール側の仕組みの名残ではないかと考えています。

復元したコードでは、各オーバーレイのディレクトリに `overlay_header.c` を置いて表現しています。

### SKCDPOSEとの関係

オーバーレイのIDは、ディスク上の `SKCDPOSE.DAT` にあるリソース番号とは直接対応していないようです。
リソーステーブルの番号は、ディスク上の特定のファイルを見つけるために使います。

### ディスク上の1バイトのタグ

ディスク上の各 `.BIN` は圧縮データで、その前に1バイトの形式タグがあります。

```text
byte 0      0x01   圧縮形式のタグ
byte 1..           圧縮ペイロード
```

このタグとオーバーレイのIDプレフィックスは別のものです。
タグは展開処理で消費され、展開後のイメージとしてRAMへ配置されません。
一方、オーバーレイのIDプレフィックスはRAM上にも存在します。
この点からも、IDは圧縮・展開処理そのものの一部ではない可能性が高いと考えられます。

## ヘッダーワードの由来を考える手がかり

### 1. rodata内のジャンプテーブルのアラインメント

GCCのMIPSバックエンドは、`switch` のジャンプテーブルを次の形で出力します。

```asm
.rdata
.align 3
$Lnnn:
.word ...
```

MIPSアセンブラーの `.align` は2の指数を指定するので、`.align 3` は8バイト境界を意味します。
基準になるのは、アセンブル中のオブジェクトの現在のセクション先頭です。最終的な絶対アドレスではありません。

ディスクから展開したADDHEROのrodataには、4つのジャンプテーブルと2つのゼロワードがあります。

```text
0x04  jtbl（8エントリー）     終端 0x24
0x24  jtbl（5エントリー）     終端 0x38
0x38  00000000               パディング
0x3C  jtbl（5エントリー）     終端 0x50
0x50  00000000               パディング
0x54  jtbl（13エントリー）    終端 0x88
```

0x04を基準にすると、テーブルの相対位置は0x00、0x20、0x38、0x50で、すべて8の倍数です。
ゼロワードの位置も、`.align 3` に合わせるためにアセンブラーが入れるパディングと一致します。
0x00を基準にすると、どのテーブルの位置も8の倍数になりません。
つまり、コンパイラーのrodataセクションはオフセット4から始まっていて、オフセット0のワードはそのセクションに含まれていなかったことになります。

NIKIにも同じパターンがあります。
GOLEMはオフセット4にジャンプテーブルが1つあり、パディングのワードはありません。
GOLEM単体ではどちらの解釈もできますが、ADDHEROやNIKIと同じコンパイラー、同じフラグでビルドされています。

### 2. コンパイラーが違っても同じ配置になる

MOVIEはGCC 2.8.0の `-G4`、ADDHERO、NIKI、GOLEMなどの大部分はGCC 2.7.2 CDKの `-G0` でコンパイルされています。
どちらも、オフセット0にヘッダーワード、オフセット4にコンパイラーが生成したrodataがあります。

### 3. ロードアドレスが違っても同じ配置になる

FIELD、WSEL、WMAP、TITLE、CHECKPSは、0x80140000ではなく0x8004FC70に読み込まれます。
それでも、オフセット0にワードがあり、それぞれの本体はオフセット4から始まります。

### 4. このリポジトリでのビルド結果

| 試した配置 | 結果 |
|---|---|
| ジャンプテーブルと同じCファイルに通常の `const s32` を置く（GOLEM） | ワードの後に4バイトのパディングが入り、後続の全アドレスがずれる。SHA-1不一致 |
| 定数だけのCファイルを分け、最初にリンクする | 北米版の全17オーバーレイでバイト単位の一致 |
| ワードを `rodatabin` として置く（変換前のGOSUB） | バイト単位の一致 |
| 定数に `__attribute__((section(".sdata")))` を付け、`.sdata` を最初に配置する（変換前のGOLEM、NIKI、ADDHERO） | バイト単位の一致 |
| 通常の定数を置き、`-G0` のオーバーレイを `-G4` でビルドする（ADDHERO） | ワードは `.sdata` に移るが、コードの159命令が変わり、不一致 |

ワードをジャンプテーブルと別のrodataセクションに置く構成は、どれも一致します。
同じセクションに入れる構成では一致しません。

## 仮説

### A. メインのCファイルに普通の定数として置いた

```c
const s32 overlay_id = 20;
```

rodataがジャンプテーブルで始まるオーバーレイでは、この方法は成り立ちません。
コンパイラーは定数を `.rdata` に置き、テーブルの前に8バイト境界までのパディングを入れます。
ディスクのデータには、そのパディングがありません。
GNAME、GOVER、TITLEのように、ワードの後に来る最初のrodataが4バイト境界だけを必要とする場合には成立します。
ただし、それも再現できるというだけで、元の実装がそうだったという証拠にはなりません。

### B. コンパイラーのsmall-data配置を使った

`-G4` では、GCCは4バイトの定数を `.sdata` に置きます。
独立したセクションになるので、リンカーで先頭へ配置できます。
ただ、ほとんどのオーバーレイは `-G0` でビルドされており、`-G4` を強制するとコードも変わるため、全体に共通する仕組みとは考えられません。
また、リンクスクリプトで `.sdata` を `.rdata` より前に置く必要があります。これはPSY-Qの標準の順序ではありません。

### C. 別のオブジェクトを最初にリンクした

オーバーレイごとに、ワードだけを定義する1行のCファイルを用意し、PSY-Qのリンクファイルの先頭に指定する方法です。
リンクの開始アドレスは、そのままロードアドレスになります。
ヘッダー用オブジェクトのrodataは4バイトで終わり、次のオブジェクトのrodataはロードアドレス+4から始まります。
次のオブジェクトは、そこを基準に自分のアラインメントを持ちます。
この構成で、すべてのオーバーレイの実際のバイト列を再現できます。

### D. リンク後の処理でワードを先頭に付けた

オーバーレイをロードアドレス+4から始まるようにリンクします。
リンク結果を生のバイナリにした後、先頭に4バイトのIDを書き足してから圧縮します。
この方法でも、実際のバイト列を再現できます。

一見すると、こちらが一番ありそうにも思えます。
ただし、デバッグやシンボルの確認時に、4バイトのずれを意識する必要があったことになります。
開発チームにそうした手間を増やす仕組みだったとすると、実用上は少し考えにくくなります。

## 採用した考え方

CとDは、リンク結果が同じバイト列になるので、バイナリだけでは区別できません。
どちらが開発上の選択として自然かを考え、このプロジェクトではCを採用しています。

- Cでは、リンクの開始アドレスがそのままロードアドレスです。
  Dでは、すべてのリンクファイルで4バイト先を開始位置にし、ファイルオフセットからアドレスを求めるツールや人もヘッダーを意識する必要があります。
  復元したコードには、その手間を前提にしていたことを示すものがありません。
- 復元したコードは、インラインアセンブリを使わない通常のCです。1行のCファイルを置く方法は、その構成にも合います。
  リンク後にIDを付けるツールを作るなら、既存の圧縮ツールとは別に、オーバーレイごとのIDテーブルとリトルエンディアンで書き出す処理が必要です。
- IDの並びはディスク上の順序よりも開発時の順序に見えます。ソースの近くで番号を管理していた、と考えると自然です。
  モジュールごとの小さなCファイルは、その番号を記述する場所にもなります。
- コンパイラー、フラグ、ロードアドレスが違っても同じ配置になる点も、Cで説明できます。
  ヘッダー用のオブジェクトは、その3つに依存しません。

Dの利点は、ソースに専用ファイルを残さずに済むことです。
ただ、それよりも4バイトのずれを管理する手間のほうが大きいと判断しています。
AとBでは、観測した配置を全体として説明できません。

これは復元時のモデルの選択で、元の実装の証明ではありません。
ディスクに残ったマップファイルやシンボルファイル、元のヘッダー用オブジェクトやID付加ツールの名前を含むデバッグ文字列など、
バイト列以外の証拠が見つかれば、見直す必要があります。

## 実装

### ソース

各オーバーレイの `src/overlays/<name>/overlay_header.c` に、次の定義と説明コメントだけを置きます。

```c
const s32 g_<name>_overlay_id = <id>;
```

このファイルには、ほかの定義を入れません。
内容を増やすとヘッダー用オブジェクトの `.rodata` のサイズやアラインメントが変わり、オーバーレイ全体の配置がずれてしまいます。

MOVIEを含むすべてのオーバーレイで、この定数はGCC 2.7.2 CDKの `-G0` でコンパイルし、必ず `.rodata` に置きます。
`-G4` では4バイトの定数が `.sdata` に移るため、標準とは違うセクション順序が必要になります。

### Splatの設定

各オーバーレイのYAMLでは、`vram` をロードアドレスにし、セグメントの `start` を0x1にして圧縮形式タグを飛ばします。
先頭の2つのサブセグメントは次のとおりです。

```yaml
- [auto, c, overlay_header]
- [0x1, .rodata, overlay_header]
```

`auto` のCサブセグメントにより、splatはリンカーのエントリーとobjdiffの比較対象を生成するための翻訳単位を認識します。
`.rodata` のサブセグメントは、ファイルオフセット0x1から0x5までをその翻訳単位に対応付けます。
オーバーレイ本体の開始位置は、以前と同じ0x5です。
`section_order` は標準のまま（`.rodata` が先頭）で、`.sdata` を先に置く必要はありません。

### ビルド登録

`mk/overlay-registry.mk` の `overlay_<name>_gcc_272_cdk_g0_srcs` では、`overlay_header.c` を最初に登録します。
本体をGCC 2.8.0の `-G4` でビルドするMOVIEでも、ヘッダーファイル用には独立した `gcc_272_cdk_g0` の登録を用意します。

### シンボル

各 `config/<version>/symbols/<name>_symbol_addrs.txt` で、ロードアドレス（0x80140000または0x8004FC70）に
`g_<name>_overlay_id` を定義します。

## まだわかっていないこと

- 開発版でこのヘッダーワードを読む処理はあったのでしょうか。
  製品版の実行ファイルには利用箇所が見つかっていないため、デバッグやディスク確認のための仕組みだった可能性が高そうです。
- ID 0から3は、ディスク上の何かに対応しているのでしょうか。
  メイン実行ファイルのエントリーポイントには、このようなワードはありません。
