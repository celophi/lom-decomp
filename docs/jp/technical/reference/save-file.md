# セーブファイルの形式

[日本語ドキュメント](../../README.md) | [English](../../../en/technical/reference/save-file.md) | [ADDHEROオーバーレイ](../architecture/addhero.md) | [テキストテーブル](text-tables.md)

『聖剣伝説 LEGEND OF MANA』は、1つのセーブをメモリーカード上の1つのファイルとして保存します。
エミュレーターのメモリーカード管理画面を開いたことがあれば、小さなアニメーションのアイコンと主人公の名前が付いた、2ブロックのエントリーとして見たことがあるはずです。
このページでは、そのファイルの中身、よく使う値の場所、編集したときに直す必要があるものを説明します。

数値はすべて、PlayStationのほかのデータと同じくリトルエンディアンです。
オフセットはセーブファイルの先頭からの位置です。
ツールが独自のヘッダーを付けてセーブを書き出す場合は、先にそれを飛ばしてください。セーブファイル自体は `SC` という文字で始まります。

## 全体の構成

セーブは常に16 KiBで、これはメモリーカードの8 KiBのブロックちょうど2つ分です。
次の4つの部分に分かれています。

| オフセット | サイズ | 内容 |
|---|---|---|
| `0x0000` | `0x180` | メモリーカードのヘッダー（タイトル、アイコンのパレット、アイコンのフレーム） |
| `0x0180` | `0x3260` | セーブデータ本体 |
| `0x33E0` | 4 | チェックサム |
| `0x33E4` | 4 | マジック値（`ANA` の3バイトと0） |
| `0x33E8` | 残り | 未使用。ファイルを `0x4000` まで埋める |

ヘッダーはPlayStation標準の形式なので、BIOSやメモリーカード管理ツールで表示できます。
その後ろは、すべてこのゲーム独自のデータです。

## ファイル名

ゲームは、製品コードの後ろにカウンターを付けてセーブに名前を付けます。

```text
BISLPS-02170 1A +3
^            ^  ^^
|            |  |+-- 一覧に表示されるセーブ番号
|            |  +--- 「+」または「-」（後述）
|            +------ 16進数のセーブカウンター（先頭の0は付けない）
+------------------- 製品コードのプレフィックス
```

実際の名前にスペースはありません。区切りがわかるように入れているだけです。

| 名前 | 意味 |
|---|---|
| `BISLPS-02170...` | 日本版の通常のセーブ |
| `BISLPSP02170...` | ポケットステーションのミニゲーム（リング・りんぐ・ランド）のセーブ |
| `BISLPS-02170DUMMY` | セーブを書き込んでいる間に使う一時ファイル |
| `AKIdummy` | 一覧に出る「空き」の新規セーブ枠 |

北米版では、同じ場所に `BASLUS-01013` を使います。

新しいセーブには、カード上の既存のセーブより大きいカウンターが付きます。読み込み画面は、これを使って最新と最古のセーブに印を付けます。
「+」か「-」かは、`0x01A8` にあるオプションのビット2で決まります。このビットは、新しいゲームを始めるスクリプトがビット3と一緒に立てます。
「+」の付いたセーブには、一覧に小さな印が表示されます。
両方のビットが立っていると、そのセーブを読み込んだときに、シーンへ直接入らず、ワールドマップの選択画面へ進みます。
これがプレイヤーにとって何を意味するのかは、まだ突き止めていません。

セーブの途中でゲームが止まったり電源が切れたりすると、`DUMMY` のファイルが残っていることがあります。
セーブ画面は、カードを読む前にこれを削除します。

## メモリーカードのヘッダー

| オフセット | サイズ | 内容 |
|---|---|---|
| `0x0000` | 2 | `SC`（PlayStationのセーブを示す印） |
| `0x0002` | 1 | アイコンのフラグ。このゲームは2フレームのアニメーションアイコンを使う |
| `0x0003` | 1 | ブロック数 |
| `0x0004` | 64 | メモリーカード管理画面に表示されるタイトル。32バイト×2行、シフトJIS |
| `0x0060` | 32 | アイコンのパレット（16色） |
| `0x0080` | 256 | 16×16のアイコン2フレーム（1ピクセル4ビット） |

タイトルは、BIOSが使うシフトJISで書かれています。
ゲーム内のテキストとは別の文字コードです。ゲーム内のテキストについては[テキストテーブル](text-tables.md)を参照してください。

書き込みが終わったセーブのタイトルは `聖剣伝説−−Ｎｏ．` で始まり、その後にセーブ番号、プレイ時間、主人公の名前が続きます。
オプションのビット2が立っていると、2つ目のダッシュが♪に置き換わります。ファイル名に「+」を付けるのと同じフラグです。

ゲームがセーブを書き込んでいる間、タイトルは `聖剣伝説破壊Ｎｏ．` になっています。
最後の手順で本来のタイトルに戻すので、`聖剣伝説破壊Ｎｏ．` のままのセーブは書き込みが中断されたものです。
チェックサムは本来のタイトルで計算されているので、そのセーブはチェックサムも合いません。

## セーブデータ本体

セーブデータは `0x0180` から始まります。
最初の部分は短い概要です。
セーブ画面は詳細ウィンドウを表示するために各ファイルのこの部分だけを読むので、ここを変えると読み込み画面の表示は変わりますが、ゲームの中身が変わるとは限りません。

### 概要と進行状況

| オフセット | サイズ | 内容 |
|---|---|---|
| `0x0180` | 21 | 主人公の名前。セーブ時に主人公のキャラクターレコードからコピーされる |
| `0x0197` | 1 | 使用中の概要レコードの数（`0x32E0` を参照） |
| `0x0198` | 4 | 現在のシーンの出現地点（下位25ビット）と、パーティーの1つ目のアイコン（上位7ビット） |
| `0x019C` | 2 | 現在のシーンのサウンドバンク |
| `0x019E` | 1 | 現在のシーンのサブBGM |
| `0x019F` | 1 | 読み込み画面のパーティーアイコンのパレット |
| `0x01A0` | 4 | BGMのトラック（下位18ビット）と、パーティーの2つ目と3つ目のアイコン（その上にそれぞれ7ビット） |
| `0x01A4` | 2 | シーンID |
| `0x01A6` | 1 | オブジェクトID |
| `0x01A7` | 1 | BGMのID |
| `0x01A8` | 4 | オプション。ビット0が振動、ビット1がモノラル、ビット2と3は新しいゲームを始めるスクリプトが立てる |
| `0x01AC` | 4 | ルク（所持金）。上限は10,000,000 |
| `0x01B0` | 4 | プレイ時間（1/60秒単位） |

プレイ時間は簡単に読めます。216,000で割ると時間、3,600で割ると分になります。
216,000がちょうど1時間です。

読み込み画面は、場所の名前をセーブに持っていません。
`0x01A0` のBGMのトラックを使って表から名前を引くので、トラックと場所はセットで変わります。

パーティーのアイコンが `0x7F` なら、その枠は空です。
アイコンの0と1は2人の主人公、2〜`0x0D` はパーティーに加わるほかのキャラクター、`0x0E` 以降はペット、`0x4F` 以降はゴーレムです。

### 技と能力

| オフセット | サイズ | 内容 |
|---|---|---|
| `0x01B4` | 44 | 習得した必殺技。武器の種類ごとに32ビットのマスク |
| `0x01E0` | 12 | 習得したアビリティ。1つにつき1ビット |
| `0x01EC` | 88 | 各アビリティの熟練度（0〜100） |
| `0x0244` | 11 | 各武器の種類の熟練度（0〜100） |

### 識別情報

どのゲームにも識別情報があり、2Pの主人公の機能で重要になります。

| オフセット | サイズ | 内容 |
|---|---|---|
| `0x024F` | 1 | コードではセーブスロットと呼んでいる。2Pの画面は、値が合わないとバージョン違いとして扱う |
| `0x0254` | 2 | ゲームID。新しいゲームを始めたときに決まる乱数 |
| `0x0256` | 2 | セーブID。セーブするたびに決まる乱数 |
| `0x0258` | 4 | 今のゲストの主人公を読み込んだセーブのゲームIDとセーブID |
| `0x025E` | 2 | ゲストの主人公を読み込むと1になる |
| `0x0260` | 4 | ワールドマップの選択画面で選んだマス（列 + 行 × 19） |

友達があなたの主人公を自分のゲームに読み込むとき、2Pの画面はまずゲームIDを確認します。
それが友達自身のゲームと同じなら、同じ主人公なので読み込みを断ります。
後でゲストを書き戻すときは、ゲームIDとセーブIDが `0x0258` と一致するセーブを探します。
カードにほかの『聖剣伝説 LEGEND OF MANA』のセーブがあっても、こうして元のファイルを見つけます。
この値を書き換えると、ゲストは帰る場所をなくしてしまいます。

### ワールドの状態

| オフセット | サイズ | 内容 |
|---|---|---|
| `0x0264` | 512 | スクリプト変数128個（1個32ビット） |
| `0x0464` | 1 | これまでに配置したランドの数 |
| `0x0465` | 1 | 主人公のレベル |
| `0x0466` | 2 | 曜日（下位7ビット） |
| `0x0468` | 8 | イベントのフラグ |
| `0x0470` | 768 | ランドのレコード64件（1件12バイト） |

### パーティー

パーティーの枠は3つあり、それぞれ592バイト（`0x250`）のキャラクターレコードです。

| オフセット | 枠 |
|---|---|
| `0x0770` | 主人公 |
| `0x09C0` | ゲスト（参加しているときは2Pの主人公） |
| `0x0C10` | 仲間（ペットまたはゴーレム） |

キャラクターレコードの中身は次のとおりです。

| レコード内のオフセット | サイズ | 内容 |
|---|---|---|
| `0x00` | 24 | 名前。空なら、その枠は空き |
| `0x18` | 1 | 下位7ビットがキャラクターの種類、ビット7が操作フラグ |
| `0x50` | ... | 装備 |

ゴーレムの仲間は種類4です。
操作フラグは、友達が主人公をゲスト枠に読み込むときにはそのまま残り、ゲストを書き戻すときに主人公側で立てられます。

### アイテム

| オフセット | サイズ | 内容 |
|---|---|---|
| `0x0E60` | 6400 | アイテムのレコード100件（1件64バイト） |
| `0x2760` | 256 | 消費アイテムごとの所持数 |

### ゴーレムとペット

| オフセット | サイズ | 内容 |
|---|---|---|
| `0x2B54` | 1 | 下位4ビットがゴーレムの数、上位4ビットが最後にパーティーを離れたゴーレム |
| `0x2B55` | 1 | これまでに作ったゴーレムの数（200で止まる） |
| `0x2B56` | 1 | 使用中のロジックブロックの数 |
| `0x2B57` | 1 | パーティーにいるゴーレム。いなければ3 |
| `0x2B58` | 3 | ゴーレムのレコード3件の表示順 |
| `0x2B5C` | 160 | ロジックブロック40個（1個4バイト） |
| `0x2BFC` | 144 | 仲間のゴーレムのロジックブロックの配置 |
| `0x2C8C` | 996 | ゴーレムのレコード3件（1件332バイト） |
| `0x3070` | 4 | パーティーにいるペット。いなければ5 |
| `0x3074` | 480 | ペットのレコード5件（1件96バイト） |

ゴーレムの色（0〜31）は、レコードの `0x48` にあります。

ペットのレコードでは、先頭21バイトが名前、`0x15` が種族、`0x5C` が固有のIDです。
`0x44` の状態ワードのビット31が立っていれば、そのペットはまだタマゴで、孵化までのカウンターは `0x42` にあります。

### その他

| オフセット | サイズ | 内容 |
|---|---|---|
| `0x3254` | 128 | 解放した図鑑の項目。1項目につき1ビット |
| `0x32DC` | 4 | 戦闘のリトライ回数。-1なら数えない |
| `0x32E0` | 256 | 概要レコード4件（1件64バイト）。使用中は先頭のバイトが0以外になる |

## チェックサム

先頭の `0x33E0` バイトのどこかを変えたら、チェックサムを直す必要があります。直さないと、ゲームがセーブを受け付けません。

チェックサムは、`0x0000` から `0x33DF` までの全バイトを足し、その合計を2倍して、`0x0414E410` を足したものです。
結果を32ビットのリトルエンディアンで `0x33E0` に書きます。
`0x33E4` のマジック値は `41 4E 41 00` のままにしておく必要があります。

Pythonで書くと次のようになります。

```python
import struct

with open("save.bin", "rb") as f:
    data = bytearray(f.read())

checksum = (sum(data[:0x33E0]) * 2 + 0x0414E410) & 0xFFFFFFFF
struct.pack_into("<I", data, 0x33E0, checksum)

with open("save.bin", "wb") as f:
    f.write(data)
```

ヘッダーもチェックサムの範囲に入っているので、タイトルやアイコンを変えたときもチェックサムを計算し直す必要があります。

## メモリー上の位置

ゲームの実行中、セーブデータ（`0x0180` 以降。カードのヘッダーは含まない）はRAMに置かれています。
場所は日本版が `0x80043140`、北米版が `0x80042FD8` です。
エミュレーターのメモリービューアーで値を探すときは、このページのオフセットから `0x180` を引き、その場所を足してください。
たとえば、`0x01AC` のルクは、日本版では `0x8004316C`、北米版では `0x80043004` にあります。

## まだわかっていないこと

- **`0x024F` のバイト。**
  コードではセーブスロットと呼んでいますが、2Pの画面は、実行中のゲームと値が合わないとセーブデータのバージョンが違うと表示します。
- **「+」のセーブ。**
  「+」を決めているフラグはわかっていますが、プレイヤーにとっての意味はわかっていません。
- **キャラクターレコードの操作フラグ。**
  いつ立つかはわかっていますが、ゲストの主人公に対してゲームがどう使うかは正確にはわかっていません。
- **ランドのレコードの3バイト目。**
  コードはここに配置した順番を記録していますが、ここを読む処理をすべて確認したわけではないので、ほかの情報も入っているかもしれません。
- **ペットの状態ワードの残り。**
  わかっているのは、タマゴを表すビット31だけです。
  ペットのレコードの `0x44` にある、それ以外のバイトにはまだ名前を付けていません。
- **未解析の範囲。**
  `0x0195`〜`0x0196`、`0x0250`〜`0x0253`、`0x025C`〜`0x025D`、それにアイテムの所持数とゴーレムのデータの間にあるメニュー関係のデータの周辺など、いくつかの範囲はまだ調べていません。

このページの元になっているCの定義は [saved_game.h](../../../../include/saved_game.h) にあります。構造体を直接読みたい場合はそちらを参照してください。
