# シーンのレイアウトと出現条件

[日本語ドキュメント](../../README.md) | [English](../../../en/technical/architecture/scene-layouts.md) | [シーン抽出ツール](../reference/scene-extractor.md)

『聖剣伝説 LEGEND OF MANA』の宝箱を見れば、どこにあるか、開けたかどうかはわかります。
ただ、抽出したデータからそれを読み取るには、もう少し説明が必要です。
シーンファイル、レイアウト、レコード、それに `0x0BC0` のような値が出てきます。
まずはそれぞれが何を表しているのかを押さえてから、出現条件を見ていきましょう。

シーンから始めて、その中にある1つのレコードまで順にたどります。
その後、実際の宝箱を例に、ゲームがそのデータをどう使うのかを確認します。

シーンは、ゲームが読み込むマップや部屋に当たります。
ここで扱うシーンファイルは `ANA/INFO_*` にあり、拡張子は `.IMG` です。
画像、テキスト、スクリプト、レイアウトなど、いくつかの種類のデータが入っています。

レイアウトは、レコードを並べたリストです。
それぞれのレコードには、そのシーンに配置するものや、有効にする処理が記述されています。
キャラクターや宝箱のようなアクターもあれば、イベントや、スクリプトで動く別の処理もあります。
ここでいうアクターは、ゲーム内に配置して制御できるオブジェクトのことです。人である必要はありません。

```text
シーン IMG
    レイアウト
        レコード 0
        レコード 1
        レコード 2
        ...
```

このデータを、コードでもドキュメントでも「レイアウトレコード」と呼びます。
CコードとPythonの抽出ツールでは、どちらも型名を `FieldLayoutRecord` にしています。
Cの `FieldSceneLayout.records` に並んでいるのが、このレイアウトレコードです。
これらは復元したコードで使っている名前で、元の開発者が使っていた名前はわかっていません。

レコード1件の大きさは48バイトです。
処理の種類、条件、位置、使用するリソースの設定、制御に使うスクリプトやパラメーターが入っています。
どの項目を使うかは、レコードの種類によって変わります。
たとえば、スクリプトだけを実行する処理なら、画面に表示するアクターを作る必要はありません。

そのレコードを使ってアクターや処理を有効にするかどうかを決めるのが、条件です。
条件には、次の3つのフィールドがあります。

| フィールド | ゲームに伝えること |
| --- | --- |
| `variable_ref` | 読み取る変数を指定する参照 |
| `minimum` | 条件を満たす最小値 |
| `maximum` | 条件を満たす最大値 |

ゲームは、参照先の変数の現在値を読み、その値が指定された範囲に入っているかを調べます。
最小値と最大値そのものも範囲に含みます。
最小値が2、最大値が5なら、2、3、4、5のどれでも条件を満たします。
これは比較の説明用の例で、特定のシーンの値ではありません。

Cコードでは、次のように比較しています。

```c
if ((value >= layout_record->condition.minimum) &&
    (value <= layout_record->condition.maximum))
```

ここで `value` に入っているのは、ゲームがメモリから読み取った値です。
最小値と最大値は、レイアウトレコードから取得します。

この違いを押さえておくと、後の話がわかりやすくなります。
レコードに書かれているのは、どの値を調べるかと、どの範囲なら条件を満たすかです。
調べる値そのものは、ゲームのメモリ上の別の場所にあります。
そのため、同じシーンファイルを読み込んでも、プレイヤーの進行状況によって結果が変わります。

`variable_ref` は、参照先の情報を1つの数値にまとめたものです。
末尾の `_ref` は「参照」を意味します。変数の現在値を格納しているのではなく、どの変数かを指定しています。
読み取る場所だけでなく、何ビット読むかという情報も含まれています。
参照先は、セーブ対象の変数の場合もあれば、フィールドの実行中に使う変数の場合もあります。
0か1しか入らない1ビットの値を選ぶことも、もっと大きな値を選ぶこともできます。
条件がすべてチェックボックスのように動くわけではなく、必ずセーブ対象の値を読むわけでもありません。

ここまでの説明は、シーンのレイアウトにあるレコードを処理する流れです。
パーティーメンバーや、ゲームの実行中に生成されるアクターは、別の処理で作られる場合があります。

では、実際の宝箱を見てみましょう。

使うファイルは `ANA/INFO_PRT/WAL_B020.IMG` です。
`WAL_B020` はゲーム内部のシーンのファイル名で、ゲーム画面に表示される場所の名前は、ここでは確認できていません。
このシーンのレイアウトには3件のレコードがあり、宝箱はレコード2です。
番号は0から始まるので、リストの3件目に当たります。

ここでは英語のガイドと同じ、北米版の抽出例を使います。
このシーンのレイアウト、イベントスクリプト、アクターのスクリプトは、日本版でもバイト単位で一致しています。

このシーンを抽出すると、宝箱のYAMLは
`assets/exports/us/scenes/WAL_B020/chests/002.yaml` に出力されます。
その中から、いくつかの項目を抜き出すと次のようになります。

```yaml
x: 395
z: 180
item_id: 0x0096
collection_variable_ref: 0x0BC0
alternate_facing: false
condition:
  variable_ref: 0x0BC0
  minimum: 0
  maximum: 0
```

最初の2つの値は、宝箱を置く位置です。
アイテムや向きの設定はいったん置いておいて、まずは条件を追ってみます。

`0x0BC0` は、どこにある値を読むかをゲームに伝えています。
先頭の `0x` は、この数値が16進数で書かれていることを表します。
普段使う10進数にすると、`0x0BC0` は3008です。
この3008が、収集状態を表す変数の現在値というわけではありません。

この参照の場合、セーブ対象の変数が並ぶ配列 `g_field_game_state->words` から、1ビットを選びます。
この配列の要素は、1つにつき32ビットあります。
参照先を求める計算は、次のようになります。

```text
ビット位置: 3008
3008 ÷ 32 = 94、余り 0

ワード94のビット0を読む。
```

ビット0は、そのワードの一番下のビットです。
「この宝箱の中身を受け取った」というチェックボックスだと考えるとわかりやすいと思います。
チェックがなければ0、チェックがあれば1です。

この計算で参照先を求められるのは、今回の `0x0BC0` の場合です。
ほかの参照には、値の種類や格納先を示す情報も含まれています。
どの参照でも、その数値を32で割るだけで読み取る場所がわかるわけではありません。

この宝箱は、最小値も最大値も0です。
つまり、条件を満たす値は1つだけです。

| セーブ対象のビットから読んだ値 | 条件の判定 | 結果 |
| --- | --- | --- |
| 0 | 0以上0以下の範囲に入る | 条件成立。宝箱を生成する |
| 1 | 0以上0以下の範囲に入らない | 条件不成立。宝箱を生成しない |

この条件の中に、1が書かれている必要はありません。
レコードに書くのは、どの値なら条件を満たすかです。
比較する0や1は、ゲームのメモリにあるセーブ対象の値から読み取ります。

もし最小値も最大値も1なら、チェックが入っているときだけ条件を満たします。
最小値が0、最大値が1なら、この1ビットの変数はどちらの値でも条件を満たします。
実際の宝箱では、中身をまだ受け取っていない間だけ生成したいので、両方とも0になっています。

元のレコードのバイト列でも、この条件を確認できます。

```text
C0 0B         00          00
variable_ref  minimum     maximum
0x0BC0        0           0
```

変数の参照を表す2バイトは、下位バイトから順に格納されています。
そのため、`0x0BC0` は `C0 0B` という並びになります。
その後に続く2つの `00` は別のフィールドで、`0x0BC0` の一部ではありません。
現在の抽出ツールでは、この3つの値を `condition` の下に直接表示しています。
確認するために `record_bytes` を自分で読み解く必要はありません。

YAMLには、もう1つ気になる点があります。
`collection_variable_ref` と `condition.variable_ref` の両方が `0x0BC0` になっています。
この宝箱のレコードには、用途の違う2つの場所に、同じ参照が入っています。

シーンローダーは、`condition.variable_ref` を使って宝箱を生成するかどうかを決めます。
一方、宝箱のスクリプトは、レコードの `scripts` 配列のスロット5から、収集状態を記録する変数の参照を受け取ります。
抽出ツールが `collection_variable_ref` として表示しているのは、このパラメーターです。
スクリプト側でも、この宝箱に対応するセーブ対象のビットがどれなのかを知る必要があるわけです。

この配列には16個のスロットがあります。
実行するスクリプトを指定するスロットもあれば、スクリプトに渡すデータを格納するスロットもあります。
通常の宝箱で使われている共通のスクリプトでは、次のように扱います。

| スロット | 用途 |
| --- | --- |
| `scripts[4]` | アイテムID |
| `scripts[5]` | 収集状態を記録する変数の参照。最上位ビットは向きを切り替えるフラグ |
| `scripts[15]` | 初期化スクリプトの参照 |

アイテムや収集状態という意味は、宝箱のスクリプトがその値をどう使うかで決まります。
すべてのアクターのレコードで、このパラメーターのスロットが同じ意味になるわけではありません。
今回の例では向きのビットが0なので、スロット5の値はそのまま `0x0BC0` です。

条件を満たすと、初期設定を行う処理がアクターのスクリプト用レコードを準備し、
16個の値をコピーして、ローカル変数の領域を確保します。その後、開始イベントを実行待ちにします。
続いてシーンローダーが、レコードのリソースと位置の設定を使って、表示するアクターを準備して配置します。
開始イベントを実行待ちにすることで、イベントの処理から初期化スクリプトを実行できるようになります。

抽出した制御情報に `active: false` とあるのも、この流れで説明できます。
抽出データが表しているのは、ゲームがそのレコードを処理する前の状態です。
この種類のアクターでは、条件を満たしたときに `active` が設定されます。
最初の値が `false` だからといって、宝箱が出現しないと決まったわけではありません。

今回の説明はここまでにしておきます。
シーンファイルから1つのレイアウトレコードをたどり、セーブ対象の値で条件を判定して、
アクターとスクリプトを準備するところまで確認しました。
宝箱を開けてアイテムを渡す処理は、この後のスクリプトの仕事です。
収集状態のビットを変更すると、まずゲームのメモリ上の状態が変わります。
その変更がセーブファイルに書き込まれるのは、ゲームをセーブしたときです。

ソースコードも追ってみたい場合は、次の箇所から読むと流れがつかめます。

- [field_scene_transition.c](../../../../src/overlays/field/field_scene_transition.c):
  `field_load_scene_actors()` がレイアウトレコードを順に読み、初期設定を行う処理を呼び出します。
- [field_interaction_start.c](../../../../src/overlays/field/field_interaction_start.c):
  `field_install_actor_action()` が条件で指定された変数を読み、値が範囲内かを調べ、条件を満たしたレコードの初期設定を行います。
- [field_script_operands.c](../../../../src/overlays/field/field_script_operands.c):
  `field_read_script_var()` が `field_resolve_script_var()` で参照先を求め、その値を読み取ります。
- [field_interaction_start.h](../../../../include/field_interaction_start.h):
  `FieldLayoutRecord` と、そのフィールドを定義しています。
- [field_scene.py](../../../../tools/scenes/field_scene.py):
  `FieldLayoutRecord.chest_yaml()` が、宝箱のレイアウトレコードを、この例で使った読みやすいYAMLに変換します。
